# Contributing

## Dev Loop

```bash
git clone ...
cd mailbridge
make build
make test
make lint
```

## Правила коммитов

- Imperative: `feat:`, `fix:`, `docs:`, `refactor:`
- Кратко: что и зачем

## Правила веток

- **Прямой push / merge в `main` запрещён** — `main` защищена на GitHub, все изменения только через PR.
- Одна задача — отдельная ветка от актуального `main` (`fix/...`, `feat/...`, `docs/...`).
- **Green CI обязателен:** merge только после того, как Actions/CI полностью зелёная (оба джоба CI — Lint и Test — успешны). CI красная = merge запрещён, сначала починить на ветке.
- Мерж только после ревью; после мержа ветка удаляется.

## Правила CI/CD (gate)

- CI: `.github/workflows/ci.yml` → джобы `Lint` (golangci-lint + npm lint + build) и `Test` (`go test -race`).
- **На `main` НЕТ required status check** (проверено по API 2026-09-16: `required_pull_request_reviews=0`, обязательные статусы не установлены) → «Green CI обязателен» это **наша дисциплина, не блокировка GitHub**: мерджим ТОЛЬКО когда `gh pr checks` зелёный, и CI на HEAD не пропущена сбоем.
- **Doc-only изменения (md/docs/archive) — без прогона CI:** `ci.yml` имеет `paths-ignore` для них (экономия ~2–4 мин на каждый такой PR). Любой PR с кодом (go/vue/Makefile/CI) CI запускает в полном виде — проверяй, что он запустился; если на кодовый PR CI не стартовала — это баг правил, чинить, а не мержить «вслепую».
- `go` lint (golangci-lint, gofmt) и `npm run lint` обязаны проходить до мержа.
- Коммит не считается готовым, пока `gh run list` для его head sha не green.
- После мержа убедиться, что push-запуск на `main` тоже green (иначе чинить отдельной веткой).

## Правила релизов

- **Релиз — минорный `0.x.y` (до v1.0.0).** До v1 меняется архитектура и API, поэтому релизы минорные; выход v1 — отдельное решение.
- После мержа PR в `main` делаем:
  1. CHANGELOG: секция `[0.X.Y]` с датой (обязательно, входит в notes релиза),
  2. **Тег `v0.X.Y` на смерженный commit main** — он запускает workflow `Release` (`.github/workflows/release.yml`): `make build` → GitHub Release + бинарник (asset `mailbridge`) автоматически,
  3. Проверка: `gh run list --workflow release.yml --limit 1` green, `gh release view v0.X.Y --json assets`.
- Версия в бинарнике (после мержа PR со сменой кода):
  тег `v0.X.Y` → workflow `Release` (fetch с полной историей) → `git describe --tags --abbrev=0` → Makefile `VERSION` (префикс `v` срезан: `0.X.Y`) → ldflags → `internal/version`;
  проверка: шаг «Version check» сравнивает вывод `./build/mailbridge version` с тегом.
- Локальный (offline) вариант: `make build && gh release create v0.X.Y build/mailbridge --title v0.X.Y` (см. `docs/operations.md`, «Релизы»).

## Перед PR

```bash
make lint && make test
```

## Планирование

- **Живой план — единственный: `PLAN.md`** (без версии в имени): шапка «Статус» (курсор) → «Открытые шаги» → «Что НЕ делаем» → «Выпущено» (индекс, **одна строка на версию**).
- **Жизненный цикл шага** (см. «Методология разработки» ниже): OPEN (полный шаблон) → CLOSED (квитанция: решение 1 строкой + что сделано + CHANGELOG ✓, **до тега**) → RELEASED (после тега шаг **уходит в `archive/PLAN.vX.YZ.md`**, в живом плане — строка в «Выпущено»).
- Архив — история + дискуссии: `archive/` (по версиям/эпохам).
- Архитектура: `docs/adr/`.

## Методология разработки (подтверждено владельцем, 2026-09-15)

> Схема: **один живой план** (`PLAN.md`) + **архив по версиям** (`archive/`) + **три режима** работы + **чек-листы** + **стоп-гейт**. Подробности ниже; краткая сводка и промпт рестарта — в шапке `PLAN.md` и в skill `mailbridge-dev`.

### Уровень «Шаг»
Один **шаг** = одна законченная цель (фича или баг), каждый шаг **всегда** завершается коммитом/PR и обновлённым планом. Внутри шага фазы: `discuss → решение зафиксировано → кодовые коммиты → закрытие`.

### Три режима
- **Режим A — разработка по плану**: берётся незакрытый шаг (или новый шаг — см. ниже), решение зафиксировано → код → тесты + линт до коммита → CI green → PR → мерж по правилам релиза → **закрытие по чек-листу**.
- **Режим B — обсуждение/планирование**: шаг ещё открыт, решения **НЕ зафиксированы**. Агенты обсуждают, формируют «открытые вопросы» + «кандидаты», фиксируют решения; **код НЕ начинается**, пока решение шага не зафиксировано в `PLAN.md` (и не подтв.).
- **Режим C — баг**: отдельным **шагом в новой сессии** (не в текущем PR). Формат: воспроизведение → гипотезы → фикс → **проверка на том же сценарии, что и баг** → regression-тест → закрытие.

### Живой план: `PLAN.md` (не PLAN.vX.Y.md)
- Структура: `## Статус` (курсор: текущий шаг, что осталось, промпт рестарта) → `## Открытые шаги` (шаблоны) → `## Закрытые (квитанции)` → `## Что НЕ делаем` (границы) → `## Методология` → `## Выпущено` (индекс).
- **Никакой версии в имени** — одна живая копия. **Выпущенные блоки** — `git mv` в `archive/PLAN.vX.YZ.md`, в живом плане остаются **только открытые шаги + строка «Выпущено»**.

### Шаблоны шагов
```
### [ ] Шаг N — <название> (v0.x.y)     ← статус: OPEN

- **Цель:** <одна цель>
- **Открытые вопросы** (для Решения/режима B):
  1. …
- **Решения:** <НЕ ЗАФИКСИРОВАНО / зафиксировал <date>, <кратко>>
- **Кандидаты** (в режиме B, до решения):
  - Вариант A — …
  - Вариант B — …
- **План шага:**
  *Код:*
  1. …
  2. …
  *Тесты:*
  - …
- **Чек-лист закрытия:** см. «Чек-лист закрытия шага»
```
> `[x]` = CLOSED (квитанция); `[ ]` = OPEN.

### Уровень «Версия»
**Версия = тег + бинарник + релиз-пакет** — это отдельный уровень поверх шагов. Формула: **`[версия] = [шаги 0..k закрыты] → PR (тег + CHANGELOG + архив) → бинарник`**.
- **Тег** ставит владелец (см. «Правила релизов» выше).
- **Версия = MINOR** `0.x.y` до v1.0.0. **PATCH `0.x.y` = только hotfix-исправления** (не фичи); фичи = минор (см. решение v0.22.1 → v0.23).
- **Нумерация** (подтверждено): до v1.0.0 — **только минорные** релизы.
- **«Шаг = версия» (зафиксировано владельцем 2026-09-17):** каждый закрытый шаг получает **свой минорный тег** (`v0.26.0`, `v0.27.0`, …) — релизы бесплатны (каждый тег → авто-бинарник + Release), и тег = quality-гейт оформления шага, а не «экономия релизов». Блок-фича выпускается **по шагам, не одним тегом в конце** (пример: блок 7 уже ушёл в v0.25.0 вместе с закрытыми 7a–7c; следующий шаг 7d получит свой тег `v0.26.0`). Частые теги — нормально («хоть по 10 в день», до v1.0.0).

### Уровень «Хотфикс» (v0.x.(y+1))
**Hotfix — баг на уже выпущенной версии (в проде), а не новый шаг**. Зафиксировано 2026-09-17, прецедент — 6-H (v0.25.0 = 7a+7b+7c+6-H).
1. **Ветка `hotfix/<имя>` создаётся от последнего тега, стоящего в проде** (НЕ от main). Не мержим незакрытые шаги «попутно» — hotfix = один PR, только фикс + 1 RED→GREEN тест, без фич и рефакторинга.
2. `go test ./...` + `make lint` + e2e (если баг в UI) → PR на `main` → CI green → squash-merge.
3. `CHANGELOG.md` (секция `[0.x.(y+1)]`) + `PLAN.md` (квитанция хотфикса: причина, разблок, что исправлено, приёмка) — **в том же PR, до merge**.
4. **Тег `v0.x.(y+1)` — по команде владельца** → Actions (`release.yml`) собирает бинарник → владелец выкатывает на прод.
5. **Backport-проверка:** если хотфикс сделан от тега в проде, а main уже содержит следующие шаги — убедиться, что фикс присутствует в main (merge PR уже несёт его в main); при ветке от старшего по дате тега — фикс в main и так есть, тег-патч — только на прод-ветку.
**Запрет:** не «зависать в разработке» до хотфикса — hotfix режется **от тега в проде всегда**, независимо от того, что на main.

### Чек-листы
- **СТАРТА (для режима A, до кода) — 6 пунктов:**
  1. Шаг найден в `PLAN.md` (`### [ ] Шаг N`), контекст понятен (или режим B).
  2. **Решение шага зафиксировано** в `PLAN.md` (если ещё нет — режим B, решение владельца).
  3. Нет открытых PR/зависимостей от текущего шага (или они уже закрыты и смержены).
  4. `git status` — нет посторонних локальных изменений; `make lint/test` в исходном состоянии — green (иначе — зафиксировать как отдельный шаг/баг, не чинить «в лоб»).
  5. **Живой `PLAN.md` чист:** квитанции выпущенных версий — в `archive/PLAN.vX.YZ.md`, в живом файле — строки в «Выпущено»/«Закрытые» (см. п.3 ВЫПУСКА). Если живые квитанции найденных закрытых шагов ещё в живом файле — **сначала** отдельно-доковый PR «архивировать vX.YZ» (квитанции в `archive/`, строка-индекс), **потом** стартать шаг.
  6. План-ветка создана: `feat/stepN-<slug>` (или `fix/stepN-<bugslug>`).
- **ЗАКРЫТИЯ (для режима A, PR-пакет) — 7 пунктов:**
  1. **Все тесты + линт** локально (и в CI) green на **HEAD PR**.
  2. **CHANGELOG** — буллит(ы) для вёрсии (в том же PR): `### Added` / `### Changed` / `### Removed` / `### Fixed`; буллит = одна строка + (опц.) ссылка на шаг/ADR.
  3. **План `PLAN.md`** — шаг `### [x]` (квитанция): `Решение` зафиксировано, `План шага` — что сделано (кратко), `Тесты` — что покрыто; `## Статус` — курсор на следующий шаг (или «всё закрыто»).
  4. **PR** — открыт на **main** с `gh pr create` (см. workflow), `--body-file` с:
     - **Scope** (что и почему, ссылка на `PLAN.md` шаг),
     - **Изменения** (файлы/команды),
     - **Тесты** (локальные + CI green; e2e/unit),
     - **Решения/владельца** (если есть, с датами),
     - **Open questions** (если есть).
  5. **CI green** (`gh pr check 26` или `gh run list --limit 1`) — **required** (см. «Правила CI/CD»).
  6. **Стоп-гейт по тегу** — см. ниже; **тег НЕ ставится автоматически**.
  7. **Агент НЕ мержит** до явного решения владельца; при мерже — squash, `delete-branch`, после мерж — push-запуск green.
  > **Правило 8 (тег) и правило 10 (строго один шаг)** — см. в skill `mailbridge-dev` (закреплено).
- **ВЫПУСКА (для уровня «Версия», PR-пакет) — 4 пункта:**
  1. **Все шаги вёрсии** `[x]` (квитанции) + **нет** незакрытых `[ ]` в этой вёрсии (или они явно отнесены к следующей вёрсии).
  2. **CHANGELOG** — секция `[0.X.Y]` с датой (булиты + «v0.23.0 — шаги 0–5»-сводка), **в том же PR**.
  3. **Архив:** `git mv PLAN.md`-блок-вёрсии → `archive/PLAN.vX.YZ.md`, в живом `PLAN.md` — строка в «Выпущено» + новые открытые следующие вёрсии (или курсор на v0.x.y+1).
  4. **Тег** `v0.X.Y` — **по явному решению владельца** (см. правила релизов); **бинарник** — `gh release view v0.X.Y --json assets` (workflow `Release`), **проверить Version check**.

### Стоп-гейт (критично, подтверждено 2026-09-15)
**Следующий шаг НЕ начинается**, пока нет явного решения владельца по тегу текущей версии. Формула: **`[тег НЕ создан → следующий шаг НЕ стартует]`**.
- После мержа PR **агент НЕ ставит** тег и **НЕ мержит** «в лоб»; ждёт решение владельца (да/нет/перенести).
- **Ветка** на каждый шаг: `feat/stepN-<slug>` (режим A) или `fix/stepN-<bugslug>` (режим C) — **никакого** `docs/...`-конфликта с папкой `docs/` (см. урок `docs/step5-status` → `plan-step5-close` в v0.23).
- **Передача между сессиями** — по промпту рестарта в шапке `PLAN.md` + skill `mailbridge-dev` + `git log`/CHANGELOG.

### Нумерация и ветки (сводка)
- **Нумерация:** до v1.0.0 — **только минорные** релизы; **PATCH `0.x.y` = только hotfix** (§«Уровень Хотфикс»).
- **Ветки:** `feat/stepN-<slug>` (A) / `fix/stepN-<bugslug>` (C) / `hotfix/<имя>` (от тега в проде, §Хотфикс); **никакого** `docs/...` (конфликт с папкой `docs/`).
- **PR-названия:** «Шаг N (v0.x.y): …» / «fix: … (шаг M)» / «hotfix: …» (см. PR #26/#27 в v0.23, #48 в v0.25.0).
