## Правила работы (для агента) — НЕ СКИДЫВАТЬ

1. **Один шаг = один commit.** Коммит-сообщение: `step N (v0.2X): <что>`. Никаких скопов из «всего по чуть-чуть».
2. Перед шагом: `git status` чистый, ветка от `main` (`fix/...`, `feat/...`).
3. Перед коммитом: `make lint && make test`; UI-шаг — `cd frontend && npm run lint && npm test`; UI-коммиты, касающиеся фильтров/диалогов/вкладок — `npx playwright test` (сид `npm run e2e:seed` ОБЯЗАТЕЛЕН после копирования БД).
4. **main защищена** — только PR → green CI (Lint + Test) → merge.
5. **DISCUSS-шаги: кода НЕТ**, пока владелец не утвердил дизайн. Фиксация решения (кратко, в этот файл) — обязательна перед кодом.
6. После каждого шага — отчёт владельцу (коротко: что сделано, чем проверено, следующий шаг).
7. Prod (:8080) НЕ трогаем; dev :8081/:5173 — по необходимости.
8. Тег/релиз только по явному решению владельца после каждого этапа (v0.22.1 → после шагов 0–1; v0.23.0 → после 2–4 + по итогам discussion).

## Этап 1 — v0.22.1 (hotfix, баги)

### Шаг 0 — Надёжность WebSocket («экран не обновляется, когда вкладка в фоне»)

**Диагноз (уже найден, `frontend/src/stores/websocket.js`):**
- нет обработчика `onerror` — ошибка соединения молчит;
- `onclose → reconnect через 3 с`: в замороженной вкладке Chrome таймеры троттлятся, событие могло «проскочить», а таймер сработать с задержкой/в вакууме;
- **нет слушателя `visibilitychange`/`pageshow`** — при возврате на вкладку никто не форсит реконнект и **никакого ресинка нет**: события за время разрыва потеряны в вакууме;
- нет видимого индикатора «связь потеряна» (в store есть `connected` ref — проверить, показан ли он в UI; если нет — добавить в шапку).

**Что сделать:**
1. `visibilitychange` (и `pageshow`, capture) → если `ws` отсутствует/не OPEN → `connect()`;
2. `onerror` → закрыть и запустить реконнект (однако же, без лавины: backoff 3 с / 10 с / 30 с, cap);
3. при `onopen` (первое И повторное подключение) — событие в store/views: views **перетягивают данные** (tasks, inbox, comments текущей задачи) — «ресинк после разрыва»;
4. индикатор в шапке: точка/бейдж «связь» — `connected` из store;
5. юнит-тесты стора (мок WebSocket): reconnect after close, resync-signal on open, backoff;
6. e2e: сценарий «разобрать — закрыть вкладку фокуса — открыть — данные актуальны» (хотя бы через `page.evaluate` с `document.visibilityState` + `dispatchEvent`).

**Приёмка:** после возвращения из фона экран актуален БЕЗ F5; индикатор честно показывает состояние.
**Коммит:** `step 0 (v0.22.1): ws — reconnect on visibility, resync after gap, indicator`.

### Шаг 1 — Вложения теряются при создании задачи из письма (подтверждённый баг)

**Диагноз (подтверждён кодом и данными):**
- `internal/web/api.go:257` `CreateTaskFromInbox` — создаёт задачу БЕЗ копирования `inbox_attachments → task_attachments` (AI-путь, `processor.go:265`, копирует — у него 84 задач с файлами).
- **Пострадавшие (prod-данные):** задачи **133, 154, 188, 197, 255** — письма с 1–4 файлами, файлов на задачах нет. 2 — `created_manually`, 3 — `updated_by/completed_by` (всплывшие письма с файлами тоже не доезжают — копировать нужно и в update/complete paths AI).
- В остальном связность файлов OK (181 файл на 84 задачах).

**Что сделать:**
1. `CreateTaskFromInbox`: после `LinkTaskToInboxItem` — копировать вложения inbox-письма в `task_attachments` (рефактор: общая хелпер-функция копирования, использовать и в processor-путях update/complete);
2. AI-paths (update_by/completed_by): до-копировать вложения нового письма к уже существующей задаче (без дублей — по hash/filename);
3. **Backfill (скрипт SQL, идемпотентный, NOT EXISTS по attachment):** для 5 задач 133/154/188/197/255 — скопировать из `inbox_attachments`. Скрипт — в репо (`scripts/` или `data-fix/`), владельцем запускается на проде; dev — прогнать при верификации;
4. юнит-тесты store (копирование идемпотентно), e2e: письмо с вложением → «создать задачу» → файл на задаче;
5. доки: дописать в `docs/api.md`/`data-model.md` правило «вложения доезжают до задачи».

**Приёмка:** новый ручной «из письма» — файлы на месте; 5 задач откатаны; e2e-тест фиксирует.
**Коммит:** `step 1 (v0.22.1): attachments — copy on manual task create + AI update/complete paths, backfill script`.

**Релиз после этапов:** тег `v0.22.1` (решение владельца после шагов 0–1 + тесты).

## Этап 2 — v0.23.0 (малые фичи + метрика)

### Шаг 2 — Миграция `task_status_history` (фундамент всех измерений)

**Почему сейчас:** без неё не поднять ни SLA, ни «цикл задач», ни отчёт по живым данным (owner-запрос). Одна маленькая миграция открывает всё.

**Что сделать:**
1. `internal/store/sqlite/migrations.go`: `task_status_history(id, task_id, from_status, to_status, by, at)` + индексы; идемпотентно;
2. запись при каждом смене статуса — **во ВСЕХ местах** где status пишется (API, AI-пути, bulk — когда появится): единый store-метод `SetTaskStatus` (refactor прямых обновлений);
3. API: `GET /api/tasks/:id/history` — хронология;
4. доки data-model + api;
5. юнит-тесты; e2e не обязателен (API-шаг), но 1 смоук UI, что история показывается.

**Приёмка:** смена статуса из UI оставляет строку в `task_status_history`; API отдаёт хронологию; `by` — юзер (admin/hermes/system).
**Коммит:** `step 2 (v0.23): task_status_history — migration + SetTaskStatus + GET history`.

### Шаг 3 — UI: «Копировать ответ как MD/TXT»

**Запрос владельца:** сейчас невозможно скопировать текст ответа в письмо. Нужна кнопка (и выбор MD/TXT); MD близок, но Outlook — не чистый MD; **сохранять структуру, ГНЕ без фона/цветов** (зелёный фон «под спойлерами» и т.п.).

**Что сделать:**
1. в карточке задачи, на комментариях `kind=reply` — кнопка «Копировать» (иконка clipboard) → `navigator.clipboard.writeText(body)`;
2. если body — HTML-обёртка: преобразовать в **чистый MD** (сохранить списки/заголовки/ссылки, убрать фон/цвет/инлайн-стили) — юнит + визуальный смоук;
3. опция «как MD» / «как TXT» (если MD-версия длиннее ~100 символов от HTML-версии — спрашиваем, иначе TXT);
4. e2e: кнопка есть, кликнул — clipboard (мока clipboard API в e2e);
5. доки: api.md — без изменений (это UI-фича); AGENTS.md/UI-гид (если есть) — коротко.

**Приёмка:** один клик → clipboard с чистым MD; структура сохранена; цвета/фон — нет.
**Коммит:** `step 3 (v0.23): UI — copy reply as MD/TXT (paste-friendly)`.

### Шаг 4 — UI: Bulk actions (массовые действия)

**Запрос владельца:** «не хватает массового выделения задач/входящих и применения действия» — сценарий «логи арендатора → в backlog» (145 задач в backlog — это следствие). Плюс «нажатая на Backlog, почти всегда — назад кнопка к другой задаче» → UX: после bulk-действия **остаться на листе** (не прыгать/не закрывать, если не просили).

**Что сделать:**
1. checkbox per-row в таблице задач (+ «выбрать всю страницу» / «все N по фильтру»);
2. плавающая панель после >=1 выбранных: `К status...` (select: backlog/new/in_progress/completed/closed), `Удалить (архив)`, `К проекту X (если есть)`;
3. API: `PATCH /api/tasks { ids: [...], changes: {status?, project?, ...} }` (batch); идемпотентно, атомарность не обязательна (на SQLite — да, но не блокировать);
4. WS: `batch_update` (один пакет, не N событий) ИЛИ N событий — выбрать по простоте UI;
5. e2e: выбрать 3 → «в backlog» → статусы сменились, чекбоксы сбросились, **страница та же** (не перескочило на детальку);
6. доки api.md.

**Приёмка:** 10+ задач можно одним жестом забросить в backlog; «всплывшие логи» — одно действие.
**Коммит:** `step 4 (v0.23): UI + API — bulk status change, checkbox selection`.

## Этап 3 — DISCUSS (кода ДО утверждения дизайна НЕ ПИШЕМ)

### Шаг 5 — DISCUSS: Информативность AI-вердиктов + «дубль ответов»

**Факты (подтверждены данными):**
- Дублей `ai_verdict` **много** (задача 99 — 6 вердиктов, 87/88/113 — по 4) — источник «ответ 2 раза, задача закрыта». Вероятно: повторная обработка письма/цепочки (retry/повторное письмо) не имеет дедупа на уровне задач (только `inbox_items.source_id`).
- **Запрос владельца:** вердикт должен нести **оригинал обрабатываемого** (не всю цепочку, а ОБРАБОТАННОЕ, можно «…срывать под спойлер, если лонг»), + **сформулированную задачу по пункту** (для протокола совещаний — когда из одного письма 10+ задач, каждая отдельно это хорошо, но не хватает ОБРАБОТАННОГО ИСТОЧНИКА).
- Нужно: (а) де-дубль вердиктов (почему их 6 на одной задаче?), (б) формат вердикта с «оригиналом обрабатываемого» + «затронутым фрагментом/пунктом», (в) UI-подсветка «это из протокола → пункт 4».

**Вопросы владельцу (до кода):**
1. Формат: `[ОБРАБОТАНО: текст письма (до N строк)] → [вердикт AI]`? Или `[оригинал] [сформулированная задача] [рекомендация]`?
2. Дедуп: «одно письмо — один вердикт» всегда? Или повторный вердикт — «обновление» с пометкой?
3. «Спойлер» в UI — да/нет (PrimeVue — есть `<details>`? или кастом)?

**Решение:** фиксируется здесь, после — идёт в v0.23.0 как **шаг 5' (код)**.

### Шаг 6 — DISCUSS: Сроки задач (due date)

**Запрос владельца:** «в задачах иногда стоят сроки, пока не используются». Сейчас поля нет.

**Вопросы владельцу:**
1. `due_date TEXT` (YYYY-MM-DD) на задаче — достаточно? Или `due_at TIMESTAMP` (дата+время)?
2. UI: куда ставить? (форма-создание, карточка, фильтры «просроченные» / «на этой неделе»?)
3. AI: извлекать срок из письма (NLU: «к пятнице», «до 20.09») — в v0.23 или отложить?
4. SLA/напоминания: напоминание о «сегодня/завтра просрочено» — в v0.23 (связь со «сегодня/спринтом»)?

**Решение:** фиксируется здесь, после — **шаг 6' (код)** (миграция + форма + AI-extract если решим).

### Шаг 7 — DISCUSS: «Сегодня / на этой неделе / sprint»

**Запрос владельца:** «когда задач 50+, не хватает вкладки-проблема «спринт» — «сегодня, что делаю сегодня; неделя; что-то более»».

**Кандидаты (обсудить, выбрать/накидать):**
1. **Минимум (без БД-схемы):** фильтр на вкладках «Сегодня» (`due_date = today` — требует шаг 6') + «Просроченные». Частота: если у владельца «сегодня» = «new+in_progress+топ-N по приоритету», то без due_date тоже реализуется.
2. **Средний:** `task.scheduled_date` (когда планирую взяться) + UI «Сегодня/Завтра/На этой неделе».
3. **Максимум:** полноценные сprints (даты начала/конец, задачи внутри) — но это уже «планировщик», может перебить «задачи vs sprint» (риск: дубль с эпиками/модулями).
4. **Альтернатива:** «Today» = «то, что я сегодня открывал/перетаскивал в статус in_progress» (activity-based, без поля).

**Решение:** фиксируется здесь, после — **шаг 7'**.
