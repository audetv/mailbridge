### [x] Шаг 0 — Надёжность WebSocket («экран не обновляется, когда вкладка в фоне»)

**Закрыт:** 2026-09-13. Коммит в main: `a3a57bf` (PR #18). Что сделано: `onerror` + backoff 3с/10с/30с cap;
`visibilitychange`/`pageshow` → форс-реконнект сразу (бегло: таймеры троттлим
в фоне); event `resync` → views перетягивают данные БЕЗ F5 (Dashboard,
TaskDetail, Inbox); индикатор `connected` = подтверждение сервера (фрейм
`connected` после auth), а не просто open. Проверено: витест 60/60 (7 новых —
store), e2e 14/14 (3 новых — `tests-e2e/websocket-reconnect.spec.js` через
`routeWebSocket`: фон→возврат БЕЗ F5, onclose→backoff, индикатор не врёт).

**Диагноз (уже найден, `frontend/src/stores/websocket.js`):**
- нет обработчика `onerror` — ошибка соединения молчит;
- `onclose → reconnect через 3 с`: в замороженной вкладке Chrome таймеры троттлятся, событие могло «проскочить», а таймер сработать с задержкой/в вакууме;
- **нет слушателя `visibilitychange`/`pageshow`** — при возврате на вкладку никто не форсит реконнект и **никакого ресинка нет**: события за время разрыва потеряны в вакууме;
- нет видимого индикатора «связь потеряна» (в store есть `connected` ref — проверить, показан ли он в UI; если нет — добавить в шапку).

**Что сделать:**
1. `visibilitychange` (и `pageshow`, capture) → если `ws` отсутствует/не OPEN → `connect()`;
2. `onerror` → закрыть и запустить реконнект (однако же, без лавины: backoff 3 с / 10 с / 30 с, cap);
3. при `onopen` (первое И повторное подключение) — событие в store/views: views **перетягивают данные** (tasks, inbox, comments текущей задачи) — «ресинк после разрыва»;
4. индикатор в шапке: точка/бейдж «связь» — `connected` из store;
5. юнит-тесты стора (мок WebSocket): reconnect after close, resync-signal on open, backoff;
6. e2e: сценарий «разобрать — закрыть вкладку фокуса — открыть — данные актуальны» (хотя бы через `page.evaluate` с `document.visibilityState` + `dispatchEvent`).

**Приёмка:** после возвращения из фона экран актуален БЕЗ F5; индикатор честно показывает состояние.
**Коммит:** `step 0 (v0.22.1): ws — reconnect on visibility, resync after gap, indicator`.

- Дублей `ai_verdict` **много** (задача 99 — 6 вердиктов, 87/88/113 — по 4) — источник «ответ 2 раза, задача закрыта». Вероятно: повторная обработка письма/цепочки (retry/повторное письмо) не имеет дедупа на уровне задач (только `inbox_items.source_id`).
- **Запрос владельца:** вердикт должен нести **оригинал обрабатываемого** (не всю цепочку, а ОБРАБОТАННОЕ, можно «…срывать под спойлер, если лонг»), + **сформулированную задачу по пункту** (для протокола совещаний — когда из одного письма 10+ задач, каждая отдельно это хорошо, но не хватает ОБРАБОТАННОГО ИСТОЧНИКА).
- Нужно: (а) де-дубль вердиктов (почему их 6 на одной задаче?), (б) формат вердикта с «оригиналом обрабатываемого» + «затронутым фрагментом/пунктом», (в) UI-подсветка «это из протокола → пункт 4».

**Вопросы владельцу (до кода):**
1. Формат: `[ОБРАБОТАНО: текст письма (до N строк)] → [вердикт AI]`? Или `[оригинал] [сформулированная задача] [рекомендация]`?
2. Дедуп: «одно письмо — один вердикт» всегда? Или повторный вердикт — «обновление» с пометкой?
3. «Спойлер» в UI — да/нет (PrimeVue — есть `<details>`? или кастом)?

**Вопросы владельцу (до кода):** — отвечены, см. Решение ниже.

**Решение (зафиксировано 2026-09-14, утверждено владельцем):**
1. **Автор** — не `user`: реальный отправитель письма (`inbox_items.from_name` + `<from_contact>`). Чинится в AI-оркестраторе (verdicts.go: update/complete-paths). Старые 83 строки `author='user'` НЕ мигрировать: UI выводит отправителя по `inbox_item_id` (у всех присутствующий) + бейдж «AI-саммари».
2. **Затронутый фрагмент** — новое LLM-поле `quote` (дословные 1–2 строки из письма-ответа) в JSON-контракте (оба buildPrompt-пути). Хранится в `verdict_json` комментария отправителя, рендерится blockquote над саммари. `body` остаётся чистым саммари → копирование MD/TXT не ломается.
3. **Оригинал письма — НЕ в body коммента.** Лениво из `inbox_items` (у комментa уже `inbox_item_id`); секция «Оригинал письма ▸» в карточке комментa, **свёрнута по умолчанию**, механизм аккордеона как «Оригинальное письмо» в TaskDetailView.
4. **Дубли вердиктов** — НЕ дедуп: «6 на task 99» = 6 разных писем (сверено с БД), пара «саммари-отправителя» + ai_verdict остаётся для каждого письма.
5. Пары «user-саммари + AI-вердикт» сохраняются (дубль-ок по решению владельца 2026-09-14).

**ПРАВКА (зафиксировано 2026-09-14 23:55, уточнено 15.09 00:20, решение владельца, задача 378):**
**AI-вердикт (ai_verdict) = ТОЛЬКО текст саммари** (`body`). Из него УБРАНО:
- «Оригинал письма» (detail/спойлер) — комментарий ВСЕГДА про письмо, стоящее СВЕРХУ, дублировать мусор;
- вложения комментария — блок вложений из письма не выносится в AI-вердикт (финальный фикс 15.09: «Там останется только вердикт»); блок вложений остаётся у legacy AI-саммари `author='user'` (там это комментарий с письмом/вложениями).
- quote-фрагмент из `verdict_json` (blockquote «Затронуто в письме»);
- вложения письма — «ни detail со спойлером, ни приложенных файлов не требуется».
**detail «Оригинал письма» ВЕРНУТ в саммари-комментарий `user`** (автор='user' + inbox_item_id — именно там письмо смотрят; было в v0.22/v0.23 dev, удалено ошибочно 15.09 и восстановлено по требованию владельца).
«Новая часть письма» (что реально написал отправитель, а не простыня его клиента) — в превью карточки «Оригинальное письмо» СВЕРХУ: `newMessagePartOf(body, prevBody)` = diff с предыдущим письмом треда + отсечение по первой подписи/«Просьба при ответе» + fallback «… + хвост письма». Проверено на #474/473 (задача 378): 24633 зн → 32 зн «вместо этой, ту, что во вложении». «Показать полностью» остаётся. Хранение/цепочки — НЕ ТРОГАТЬ (реестр `threads`, `thread_id` — ок).

**Решение (заполняется после обсуждения, правило 10):** ЗАФИКСИРОВАНО (ссылка выше) — следующий подшаг: код.
